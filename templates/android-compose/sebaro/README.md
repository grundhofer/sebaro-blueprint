# sebaro design export: sebaro (profile android)

A copy of the sebaro design system for an Android app in Compose: the copy is the source of one Gradle library module of the product (namespace de.sebaro_ventures.design), the same bytes in every app. **Do not edit these files.** `checks/update-copy.mjs` fetches a newer release and writes this folder anew (section *Keep in sync*), and `CHANGES.md` says, release by release, what a product does after an update. `sebaro-export.json` lists every file with its sha256, and the packs of this copy. What a product needs to adopt the copy is in this README and in the files it names here; the last section is for the maintainers of sebaro alone. Generated by `tools/export_system.py` 1.34.0 (status of the system: draft).

## Moving an app here: three calls to change

An app that comes from a `--target android` copy, the Maven package or a copy of release v1.14.0 changes three calls. The first compiles, keeps the tests green, passes `checks/lint-android.sh` and goes wrong where only the screen shows it; the two others stop compiling with token contract 2.0, because the copy lists no product. What else changes for app code is under *The Gradle module*.

**1. The sign tile wants the complete tile drawable.** Since design round 7 (D143/D144, 2026-11-11) `SbSignTile` no longer draws a tile behind a tinted glyph: it draws the drawable it is given, as it is. It wants `sb_sign_<id>` (32 dp and above; `sb_sign_<id>_small` below), which the product kit writes, and so does `SbAboutHead`, whose `glyph` goes to the same wrapper. An app that still passes its notification glyph gets a bare white glyph without a tile:

```kotlin
// before: the wrapper drew the tile and tinted the glyph
SbSignTile(product, painterResource(R.drawable.ic_stat_notify), contentDescription = name, size = 32.dp)
// after: the drawable is the whole tile, <id> the product's id
SbSignTile(product, painterResource(R.drawable.sb_sign_<id>), contentDescription = name, size = 32.dp)
```

`ic_launcher_monochrome`, which the old wrapper took from 48 dp, is wrong in the same way. `ic_stat_notify` stays the small icon of a notification. The wrapper does not refuse the wrong drawable.

**2. `SebaroProduct.<Name>` and `SebaroProduct.fromId("<id>")` do not compile.** `SebaroProduct` is a class with a constructor and nothing else: no constant, no `entries`, no `fromId` (in release v1.14.0 `fromId` still compiled and threw when it ran). Both become the product's own constant, which the product kit writes as `AppProduct` (`SebaroProductInfo.kt`):

```kotlin
// before
val product = SebaroProduct.fromId("<id>")
// after: the kit's constant, SebaroProduct("<id>", SebaroSignTile.<Group>)
val product = AppProduct
```

**3. The `SbStart` without a product does not compile.** The old start, a centred tile that travelled into the top bar, is gone, and so is its signature `SbStart(ready, tile, content)` (release v1.14.0 kept it and showed the umbrella's colour). Give the start the product and its bare symbol:

```kotlin
// before: the tile in the middle, then in the top bar
SbStart(ready, { SbSignTile(product, glyph, contentDescription = null, modifier = it) }) { App() }
// after: the product's colour and its bare symbol
SbStart(ready, AppProduct, { SbStartSymbol(AppProduct, it) }) { App() }
```

and name the start theme in the manifest, on the launch activity or the application: `android:theme="@style/Theme.Sebaro.Start"`. It gives the window the product's colour before the first frame and, from Android 12, the system splash the same colour and symbol (`sebaro_start_theme.xml`, `values-v31/sebaro_start.xml` and `sb_splash_symbol_<id>.xml` of the kit's folder, section *Product files*). An app with a theme of its own does not replace it: its theme inherits from it, `<style name="Theme.App" parent="Theme.Sebaro.Start"/>`, where section *Platform theme* says `Theme.Sebaro`. `Modifier.sbStartTarget()` still compiles and does nothing.

**Show the start once per activity start.** A freshly composed `SbStart` always begins with its covering frame and fades over 200 ms, also with `ready = true`: after a rotation, or any other recreation of the activity, the product's colour flashes again. The wrapper does not remember that it was shown. Compose it only on the activity's first start, and lay it over the content instead of wrapping the content in a condition (a wrapper that comes and goes moves the content in the composition, and its saved navigation stack is lost on rotation):

```kotlin
// in the activity's onCreate: true on the first start, false after a rotation
val firstStart = savedInstanceState == null
setContent {
    SebaroAppTheme {
        Box {
            App()                                   // always composed, always at this place
            if (firstStart) SbStart(ready, AppProduct, { SbStartSymbol(AppProduct, it) }) {}
        }
    }
}
```

`SbStartSymbol` reads `sb_symbol_<id>` by name from the app's resources. If the app stops with „Missing product symbol resource sb_symbol_<id>“, the symbol is not among them: it comes from the product kit. Run its `build` and add the kit folder's `android/res` to the app's resource directories (section *Product files*).

## The Gradle module

A product consumes this copy as one Gradle library module of its own: `com.android.library`, namespace `de.sebaro_ventures.design`. The namespace is fixed, because the copy is the same bytes in every app: its Kotlin stands in `de.sebaro_ventures.design` and reads its resources as `de.sebaro_ventures.design.R`. The module's build file is the product's and stands **outside this folder** (a file added here fails `checks/verify-export.mjs --strict`). With the copy in `<repository>/sebaro/`:

```kotlin
// settings.gradle.kts
include(":designsystem")
```

```kotlin
// designsystem/build.gradle.kts: the module of the sebaro copy in <repository>/sebaro/ (AGP 9, built-in Kotlin)
plugins {
    id("com.android.library")
    id("org.jetbrains.kotlin.plugin.compose")
}
android {
    namespace = "de.sebaro_ventures.design"   // fixed: the copy's Kotlin reads de.sebaro_ventures.design.R
    compileSdk = 37
    defaultConfig { minSdk = 26 }             // not above the app's; below 26 the wrappers' java.time needs desugaring
    buildFeatures { compose = true }
    compileOptions {                          // Java 11 or newer: the module may take the app's version
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17
    }
}
val sebaro = rootProject.layout.projectDirectory.dir("sebaro")
androidComponents {
    onVariants { variant ->
        variant.sources.kotlin?.addStaticSourceDirectory(sebaro.dir("kotlin").asFile.path)
        variant.sources.res?.addStaticSourceDirectory(sebaro.dir("res").asFile.path)
    }
}
dependencies {
    api(platform("androidx.compose:compose-bom:<your BOM>"))   // material3 1.3.1 or newer
    api("androidx.compose.material3:material3")
    implementation("androidx.activity:activity-compose:<1.9.3 or newer>")   // BackHandler of SbScreen
}
```

```kotlin
// app/build.gradle.kts
dependencies {
    implementation(project(":designsystem"))
}
```

**The plugins.** The module names its two plugins without a version: each takes it from the root `build.gradle.kts`, where it stands with `apply false`. A Compose app has the Compose compiler plugin there already. It has `com.android.library` there only if the project already had a library module: an app that never had one adds it first, in the version catalog and in the root build file, with the version of its `com.android.application`:

```toml
# gradle/libs.versions.toml, under [plugins]; `agp` is the catalog's key of the Android Gradle plugin version
android-library = { id = "com.android.library", version.ref = "agp" }
```

```kotlin
// build.gradle.kts of the root project, inside plugins { … }
alias(libs.plugins.android.library) apply false
```

Without a catalog the root line is `id("com.android.library") version "<the app's AGP version>" apply false`. A module in a project with a catalog may write `alias(libs.plugins.android.library)` and the catalog's alias of the Compose plugin in place of the two `id(…)` lines.

**Java.** The block sets Java 17, the version a copy is compiled with before a release. Required is Java 11 or newer: with `VERSION_1_8` the module does not compile on Compose BOM 2026.08.00, whose inline functions are built for JVM 11 (it does on 2024.12.01). The module may take the app's version: set both lines to it (`VERSION_21` in an app on Java 21). Compiled with 11, 17 and 21 on both BOMs, the core copy.

`android { sourceSets["main"].kotlin.srcDir(…) }` throws a ClassCastException under AGP 9.3.1 (old source-set API); the variant API above works there. `SebaroTheme.kt` targets the material3 1.3 slots. Before a release a copy is compiled with this build file as it stands here, the core alone and with every pack (AGP 9.3.1, Kotlin 2.4.10, Compose BOM 2026.08.00 and 2024.12.01).

With the pack `charts`: `SbBoundedChartFigure`. With the pack `media`: `sbMediaLength`. With the pack `camera`: `SbFlashMenuView`, `sbDrawPhotoLine`, `sbPhotoPath`. Members of public types, in the core: `SbActionFocus.asked`, `SbActionFocus.served`, `SbCancelBackHoldState.remainingMillis (setter)`, `SbToastState.hasFocus`, `SbToastState.returnTo`, `SbValueMeasureCache.maximum`, `SbValueMeasureCache.measureCalls`, `SbValueMeasureCache.wrappingStyle`. Both lists are read from the files; `grep -rnE '\binternal\b' <this folder>/kotlin` shows every place.
- **Resources of the copy are `de.sebaro_ventures.design.R`.** App Kotlin that names one (`R.font.sebaro_…`, `R.drawable.sb_keymark_small`, with the pack `widget` `R.layout.sb_widget_small` and `R.dimen.sb_widget_…`) imports that class beside its own (`import de.sebaro_ventures.design.R as SebaroR`): with non-transitive R classes, the default, the app's own `R` does not hold them. XML and the manifest need no change: `@color/sebaro_bg`, `@style/Theme.Sebaro` and `@layout/sb_widget_small` resolve in the app's merged resources.
- **Imports stay** `de.sebaro_ventures.design…`. A copy that was exported with `--package` goes back to them.
- **The copy lists no product.** `SebaroProduct.<Name>` and `SebaroProduct.fromId("<id>")` do not exist; the product has its own constant, `SebaroProduct("<id>", SebaroSignTile.<Group>)`; the product kit writes it as `AppProduct` (`SebaroProductInfo.kt`).
- **Launcher, notification icon, sign tile and the start come from the product's own folder**, which `product/product_kit.py` writes from the declaration (section *Product files*); the app module adds that folder's `android/res` where it added `launcher/<id>/res` of the old copy. The start is five files there: `drawable/sb_symbol_<id>.xml`, `drawable/sb_splash_symbol_<id>.xml`, `values/sebaro_start.xml`, `values-v31/sebaro_start.xml` and `values/sebaro_start_theme.xml` (`Theme.Sebaro.Start`). No file of an older copy is kept: an app that carried any of the five over from a `--target android` copy deletes its own, the kit's folder is their one source.

## Platform theme

`Theme.Sebaro` (in `res/values/sebaro_theme.xml`, the dark parent in `values-night/`) colours what Compose does not draw: the window before the first Compose frame (`windowBackground` = `bg`), an `EditText`'s selection, handles and caret (`colorAccent`, `textColorHighlight`), its text menu and other platform widgets. Use it as the parent of the app's manifest theme (`<style name="Theme.App" parent="Theme.Sebaro"/>`); the splash theme keeps `@color/sebaro_splash_background`. Compose screens still take every colour from `SebaroTheme`; the `@color/sebaro_*` resources are for XML that needs a colour (a Glance loading layout, a notification's accent): never a hex value in the app. The warm tone („Papier“) is the `sebaro_warm_*` set; the theme itself follows the cool tone (an app with the warm tone sets its window ground itself).

## Widgets

With the pack `widget`.

An `AppWidgetProvider` of the app builds the widget with `sbWidgetSmall(…)` or `sbWidgetMedium(…)` (`designsystem/SbWidget.kt`) and hands it to `AppWidgetManager.updateAppWidget`; the manifest receiver names `@xml/sb_widget_small_info` or `@xml/sb_widget_medium_info` as its `android.appwidget.provider`. Pass the widget's size from `getAppWidgetOptions(id)` (`widthDp`, `heightDp`): the widget shows what fits its cell. The text follows the font size of the last update up to 125 %; above 100 % the small widget drops its sentence and the medium one its list, so put both into the content description. The layouts are RemoteViews XML because Glance's own text cannot take a font from `res/font`; a Glance app can place them with `AndroidRemoteViews` (not compiled here).38.

## Use

Every screen root is `SebaroAppTheme { … }` (`designsystem/SebaroAppTheme.kt`, spec/08 §2.2): it takes no product and registers the fonts of `res/font/` itself. Colours, type and tokens come from `SebaroTheme` (`SebaroTheme.colors` / `.typography` / `.tokens` / `.dataviz`), icons from `SebaroIcons.Outline.Search` and its siblings. The product shows in its launcher icon and where a wrapper takes a `SebaroProduct` (`SbSignTile`, `SbAboutHead`, `SbProductArea`, `SbStart`, `SbAppFrame`), never as a colour (D54).

`designsystem/` is generated from the system's spec: never edit it here (the checks report it); a change is made in the system and comes here with a release. The rules an app's own Kotlin keeps are the table of the lint under *Keep in sync*.

## Templates

With the pack `templates`. `templates/android/` is app code, not part of the module: copy the screens the app uses, with `SbTemplateScreen.kt`, into the app and give them the app's package. They use the public names of the wrappers only. `SbViewSamples.kt` with `res/values*/sb_view_templates.xml` is the reference filling, a place to start: it names the sample product „Beispiel“, reads a string by its name and packs several words into one string; an app reads its own `R.string` ids. The `outside` template builds the home-screen widget, so the pack needs the pack `widget`.

## Product files

`product/` is the product kit. With this folder and its own declaration, `sebaro.product.json`, a product makes its own files and checks them in CI. `product/PRODUCT-CONTRACT.md` describes the declaration (its schema is `product/product.schema.json`), every output and the two records.

```sh
python3 <this folder>/product/product_kit.py build sebaro.product.json --copy <this folder> --out sebaro-product --render
python3 <this folder>/product/product_kit.py check sebaro.product.json --copy <this folder> --out sebaro-product    # CI
```

`build` writes into `sebaro-product/`, a folder of the product **outside this one**, and nothing here (Python 3.10+, standard library). `--render` then draws the PNG and ICO files with `product/render.mjs`: Node 20+ and the product's own Playwright with Chromium (`npm install --save-dev playwright`, then `npx playwright install --only-shell chromium`). A product without a Node project names a folder that holds `node_modules/playwright` in the environment variable `SEBARO_PLAYWRIGHT` (any folder in which `npm install playwright` ran; `build --render` passes it on). Without the flag the build names the files that wait, and `node <this folder>/product/render.mjs sebaro-product` draws them later. `check` writes nothing and needs Python alone: exit 1 with one line per output that is missing, edited or stale. It compares the declaration by what it says, so a formatter may change its white space and the order of its keys; it compares a raster file by sha256 with the renderer's record (`sebaro-product-raster.json`) and with the SVG under `render/` it was drawn from, never by pixel. A product that keeps no raster file adds `--no-raster` (an Android app whose Play icon and feature graphic are not in its repository).

| In `outputs` | Text files | Raster files |
|---|---|---|
| `android` | `android/res/`: the launcher layers and the adaptive icon, `ic_stat_notify.xml`, `sb_sign_<id>.xml` and `sb_sign_<id>_small.xml`, `sebaro_splash.xml` (light and night), and the start: `sb_symbol_<id>.xml`, `sb_splash_symbol_<id>.xml`, `sebaro_start.xml` (`values/` and `values-v31/`) and `sebaro_start_theme.xml` with `Theme.Sebaro.Start`; `android/kotlin/SebaroProductInfo.kt` | `android/play-store-512.png` and `android/play-feature-1024x500.png` (the feature graphic) for the Play listing; the app itself needs no raster file |
| `web` | `web/`: `icon.svg`, `manifest.webmanifest`, `manifest.snippet.json`, `head.snippet.html`, `theme-color.json`; and `sign/` | `web/favicon.ico`, `web/apple-touch-icon.png`, `web/icon-192.png`, `web/icon-512.png`, `web/icon-mask.png` |
| `desktop` | `sign/`: `sign.svg`, `sign-small.svg`, `tile.svg`, `tile-small.svg`, `product.css` | `desktop/icon-1024.png` |

Beside them the kit writes `NOTICE.md`, the two records and `render/` (the drawing of each raster file). Commit the whole folder: `check` compares it.

The app module adds `sebaro-product/android/res` to its resource directories and `sebaro-product/android/kotlin` to its Kotlin sources, and its manifest names `@style/Theme.Sebaro.Start` for the launch activity. `designsystem/SbStartSymbol.kt` reads `sb_symbol_<id>` by name from the app's merged resources, and `res/raw/sebaro_symbols_keep.xml` of this copy keeps it under resource shrinking. `product/` is no source folder of the module.

An Android app needs the renderer for two files, the Play icon and the Play feature graphic, and has no Node project. Its CI runs `check` with `--no-raster` (Python alone). The two are drawn once by hand, and again when the sign or the name changes: `SEBARO_PLAYWRIGHT=<a folder with node_modules/playwright> node <this folder>/product/render.mjs sebaro-product`.

**The terms of `sebaro-product/`.** The licence file of this folder covers this folder, not the product's. The kit writes `sebaro-product/NOTICE.md`, which says it for that folder: the sign and every drawing made from it (SVG, drawable, PNG, ICO) are marks of the product, all rights reserved, not under the MIT licence of the system and not under the repository's licence unless the owner of the product says so; the code and data beside them (`product.css`, the manifest, the head snippet, the values and Kotlin files, the records) are MIT like the kit. A product in a repository under an open licence states the marks as not covered by it (a REUSE `.license` file, or an entry in its own notice); nothing else has to be stated.

## Keep in sync

A release of the sebaro design system is published as public copies, one archive per profile with every pack. `checks/update-copy.mjs` fetches the archive of this profile and writes this folder anew with the packs it should hold (Node 20+, built-ins only):

```sh
node <this folder>/checks/update-copy.mjs --check                 # changes nothing; exit 1 when a newer release exists (a scheduled CI job)
node <this folder>/checks/update-copy.mjs                         # the newest release, with the profile and the packs of this copy
node <this folder>/checks/update-copy.mjs --packs <pack>,<pack>   # the same with another choice of packs
node <this folder>/checks/update-copy.mjs --release <tag>         # one release, not the newest
```

**What changed for a product** is in `CHANGES.md` of this folder: one section per release, in plain sentences, with what to do after the update. After an update the updater prints the sections between the release this copy had and the new one; `--check` prints their headings when a newer release exists.

It reads `copies.json`, `CHANGES.md` and `sebaro-android.tar.gz` from `https://github.com/grundhofer/sebaro-blueprint/releases` (`/latest/download/<file>`; with `--release <tag>`, `/download/<tag>/<file>`; another place with `--from <folder or URL>` or the environment variable `SEBARO_COPIES`). It checks the sha256 of the archive against the index and of every file against the release's record, writes the copy into a temporary folder beside this one and swaps the two at the end, so a failed run leaves this folder as it was. It refuses while a file here is edited, added or missing, the test of `checks/verify-export.mjs --strict` (`--force` writes anyway); a dotfile and, with `--force`, a file the record does not name stay. Exit 0 written, or with `--check` at the newest release · 1 `--check`: a newer release exists, both versions are printed · 2 usage: an unknown option, profile or pack, a pack without the pack it needs (the message lists what exists) · 3 refused: local changes · 4 the release cannot be read or does not verify; nothing was changed.

The files it writes are byte for byte the files of that release for this profile and these packs. `sebaro-export.json` records the release (`release`: the tag, the archive and the updater) and the day the copy was written. The first copy of a product comes from the same file, fetched alone from the release: `node update-copy.mjs --profile android [--packs <pack>,<pack>] --out <folder>`.

### In the product's CI

This folder brings its own checks; the section *What needs what* says what each needs. These belong to every build:

```sh
node <this folder>/checks/verify-export.mjs --strict    # this folder is unchanged
python3 <this folder>/product/product_kit.py check sebaro.product.json --copy <this folder> --out sebaro-product --no-raster    # the product's files are what its declaration gives
sh <this folder>/checks/lint-android.sh <the app's Kotlin source folder>    # the product's sources keep the rules
```

The question for a newer release belongs to a scheduled job once a week, not to every build: it turns red on the day of a release, whatever the product changed. In GitHub Actions: `schedule` with a `cron` line beside `push` and `pull_request`, and this step only `if: github.event_name == 'schedule'`.

```sh
node <this folder>/checks/update-copy.mjs --check    # a newer release exists: exit 1; update with checks/update-copy.mjs, as a commit of its own
```

Keep this folder and the product's folder (`sebaro-product/`) out of the product's formatter and linter, and out of any commit hook that formats: a reformatted file here is an edited copy, one there a stale product file, and the checks above fail on both.

`checks/verify-export.mjs` checks this folder (or the export folder given as its argument) against `sebaro-export.json`: every recorded file present and unchanged. One line per finding (`FAIL  missing in target: …`, `FAIL  edited in target: …`, `WARN  not part of the export: …`) and a summary line. Exit 0 no errors, 1 a missing or edited file (with `--strict` also a file the record does not name, without it a warning), 2 usage error or a missing or unreadable `sebaro-export.json`. `--strict` never counts `sebaro-export.json` itself, dotfiles or anything in a dot folder; anything else the product puts into this folder fails it, so keep the product's own files outside. It does not look for a newer release: `checks/update-copy.mjs --check` does.

`checks/update-copy.mjs` holds a call of `fetch(`. Where this folder lies inside an app's source tree and the product checks its UI sources for network calls, leave this folder's `checks/` out of that check: nothing in `checks/` or `product/` is loaded by the app.

`checks/lint-android.sh` is the lint of the system's rules for an app's Kotlin sources (8 rules, A1-A8, counted from the ids its lines carry). It prints the offending lines and exits 1 on a violation. **A clean run prints nothing: silence with exit 0 is success.**

| Rule | What it asks |
|---|---|
| `A1` | no product colour on screens (D40): `SebaroTheme(` only inside `SebaroAppTheme`, never with `product =` |
| `A2` | `SebaroProduct` only to pick a sign tile, product area, start or app frame/template product (`SbSignTile(`; the script still lets `fromId` pass, which left `SebaroProduct` with token contract 2.0) |
| `A3` | the lime roles (`primaryAction`, `primaryActionHover`, `primaryActionPressed`, `primaryActionOutline`, `onPrimaryAction`) only in `/designsystem/` |
| `A4` | no stock M3 `Button`, `FilledTonalButton`, `ElevatedButton`, `FloatingActionButton`, `ExtendedFloatingActionButton`, `NavigationBar`, `NavigationBarItem` outside `/designsystem/` (the M3 item draws a filled pill indicator) |
| `A5` | no tinted areas: no `accentSubtle`, `successSubtle`, `warningSubtle`, `dangerSubtle`, `infoSubtle`, `textOn…Subtle`; one exception (D85): `successSubtle` / `dangerSubtle` as the line fill of a diff line that carries its `+` / `−` sign (spec/01 §1.8): the wrapper `SbDiff` (§14.26) draws it, so the lint lets these two roles, and only these, pass in `/designsystem/SbDiff.kt` (as colour lint L2 allows the two fills only in the `.sb-diff__line` rules); a hit in an app's own diff view is reviewed, not fixed; the generated `SebaroTheme.kt` defines the roles and is not linted, so an app may run the lint over a folder that holds the export |
| `A6` | no count badges: no `Badge(`, `BadgedBox(` |
| `A7` | no raw colours: `Color(0x` only in `SebaroTheme.kt` |
| `A8` | one primary action per screen: every screen root is `SbScreen`; `SbPrimaryAction(` only inside `/designsystem/` |

The script holds the shell part of each rule: what a row says beyond a pattern in a file is a review.

## For the maintainers of sebaro

A product needs nothing of this section. This copy is written from the sources of the system in the repository sebaro-foundry: `python3 tools/export_system.py sebaro --profile android [--packs <pack>,<pack>] --out <directory>`, with `--from-commit <rev>` from a commit instead of the working tree. `python3 tools/export_system.py --verify <directory>` rebuilds the copy from its profile and packs and exits 1 when a file was edited or deleted, when a source changed, when a fresh export would add or drop files, or when a gate of the system fails. A change to a file of this folder is made in those sources and reaches a product with a release (`tools/release_copies.py`). The specs, the token and icon sources, the palettes and the gates stay there.
