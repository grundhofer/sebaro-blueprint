## Plain HTML

```html
<html lang="de">   <!-- data-theme="light|dark" only for an explicit switch -->
<head>
  <meta name="color-scheme" content="light dark">
  <link rel="stylesheet" href="/sebaro/fonts/fonts.css">
  <link rel="stylesheet" href="/sebaro/tokens.css">
  <link rel="stylesheet" href="/sebaro/icons/sprite.css">
  <link rel="stylesheet" href="/sebaro/css/sebaro.css">
  <!-- + the lines of web/head.snippet.html of the site's own product folder (section Product files) -->
</head>
<body>
  <!-- icons/sprite.svg pasted here as it is (it hides itself); then: -->
  <svg class="sb-icon sb-icon--24" aria-hidden="true" focusable="false"><use href="#search"/></svg>
```

`/sebaro/` stands for wherever this folder is served. `sprite.css` sits in `@layer base`, so its position among the unlayered files does not matter. External `<use href="/sebaro/icons/sprite.svg#id">` works same-origin over http, not from `file://` (shared/ICONS-GUIDE.md §9.1). The quick start in the system's AGENTS.md §3 uses the system's own folder names; the map from those paths to this folder is in shared/ADOPTION.md.

## Parts of sebaro.css

The same rules as `css/sebaro.css`, cut into parts by the marks in the source (D102 (37)). Load the parts you need instead of the whole file, in the number order of their names; `01` always, and the last (forced colours and print) with every set. All of them together hold every rule of the whole file once; loaded together in this order they cascade like the whole file on the system's demo pages (checked in Chromium, systems/<slug>/CHECKS.md). A part that is left out leaves its components unstyled, and what it adds to the components of other parts (the window density of lists, the forced colours of every part) is missing too. Never load the whole file and parts together. The size of each part and of the whole file (bytes and gzip bytes, for a CSS budget) is in `sebaro-export.json` under `cssSizes`, written at every export; `--verify` does not compare it.

### Colour count per view (spec/03 §1.4, TEC-03)

Mark every view root with `data-sb-view="<name>"` (and `data-sb-primary-expected="0"` on a view without a primary action). `sbColourCount(view)` returns `{primary, place, status, signs, unknown, textOnColour, pass, line}`; `pass` is true with the expected number of primary-action fills, no colour without a role (`unknown` lists them) and no text on a coloured fill. Count each view in light and dark (`<html data-theme>`) and with the warm tone (`<html data-sb-tone="warm">`).

In CI (Playwright, after the page has loaded and its transitions have ended):

```js
await page.addScriptTag({ path: "<this folder>/checks/sb-colour-count.js" });
const views = await page.evaluate(() => [...document.querySelectorAll("[data-sb-view]")]
  .map((v) => ({ view: v.dataset.sbView, ...window.sbColourCount(v) })));
const failed = views.filter((v) => !v.pass);   // fail the run with failed.map((v) => v.line)
```

On a development page: `<script src="<this folder>/checks/sb-colour-count.js"></script>` at the end of the body writes each view's line („Farbprüfung: Hauptaktion 1 · … · bestanden“) into `[data-sb-colour-count="<name>"]` and counts again after `sb-theme-change`. The line is German only (a check, not UI text). Not read: pseudo-element paints (checkbox marks, chip frames, slider handles) and focus outlines.

## Share images

One share image per page with a title of its own, 1200 × 630, light ground, rendered **in the site's own build** from the one template of sebaroDesign (D96, spec/09 §18.1). The site writes a page list from its own pages; `brand/og/render.mjs` fills `brand/og/template.html` once per page and renders it in Chromium. Needs Node 20+ and Playwright with Chromium (Chromium only, like the CI under D96 (b)): `npm install --save-dev playwright`, then `npx playwright install --only-shell chromium`. Offline: every request that is not local (`file:`, `data:`) is blocked.

```sh
node <this folder>/brand/og/render.mjs --pages og-pages.json --out public/og --head build/og-head
```

`og-pages.json` follows `brand/og/pages.schema.json` (the script checks it against that file):

```json
{
  "$schema": "./sebaro/brand/og/pages.schema.json",
  "site": {
    "product": "<product>",
    "name": "<site name>",
    "origin": "https://<host>"
  },
  "pages": [
    {
      "id": "start",
      "url": "/",
      "type": "website",
      "title": "<the start page's title>"
    },
    {
      "id": "<page id>",
      "url": "/<section>/<page>/",
      "title": "<the page's own title>",
      "path": [
        "<site name>",
        "<section>",
        "<page>"
      ],
      "readingMinutes": 12,
      "date": "2026-04-26",
      "description": "<the page's meta description>"
    }
  ]
}
```

Per page it writes `<out>/<output>.png` (24-bit RGB, no alpha) and `<head>/<output>.head.html` with the head tags of spec/09 §18.1 (canonical, description and og:description when the page has one, og:type, og:site_name, og:locale, og:url, og:title, og:image absolute, its width, height and alt, twitter:card), plus `<head>/head.json` with the same tags as data for a framework. Include the snippet in the page's `<head>`; the site still writes `<title>`, the language alternates (spec/09 §18.2) and serves the PNGs under `site.origin` + `site.imageBase` (default `/og/`). Keep `--head` out of the published folder.

It fails loud (exit 1, the page id named, no image and no head snippet written for that page): a title that needs more than three lines or a word wider than its line (never cut, never set smaller; mark break points in long compounds with U+00AD), a path, name or foot wider than its line, a character sebaro Sans does not cover, a font that did not load, a blocked request, and in the written PNG a size other than 1200 × 630, an alpha channel or a ground other than `color.bg` light. Exit 2: the page list does not match the schema, or a file of this export is missing (the generator reads `brand/inline/tile-<id>.svg` of the product a page names: this export holds the demo samples' tiles; a product's own tile is `sign/tile.svg` of its product folder, and `product/render.mjs share` of a profile copy runs the generator with it). The same input gives the same bytes with the same Chromium. German and English words (`site.lang`); right to left is not supported.

## Product files

`product/` is the product kit, the same files a profile copy brings. The site that takes this export declares itself like any product, in `sebaro.product.json` (`product/PRODUCT-CONTRACT.md` describes it, `product/product.schema.json` is its schema), and the kit writes the site's own files into a folder of the site, outside this one:

```sh
python3 <this folder>/product/product_kit.py build sebaro.product.json --copy <this folder> --out <folder> [--render]
python3 <this folder>/product/product_kit.py check sebaro.product.json --copy <this folder> --out <folder>
```

`<folder>/web/` goes to the site root: `icon.svg`, the manifest, `head.snippet.html` for the page head, and with `--render` (Node 20+ and Playwright with Chromium) `favicon.ico` and the PNG icons. `<folder>/sign/` holds the site's sign, its tile and `product.css`, the scope of its own id, to load after `tokens.css`. `check` needs Python alone and exits 1 when a file is missing, edited or stale. This export brings no file of a product: until export 1.29.0 `--product <id>` wrote `brand/site-root/` here.

## Keep in sync

```sh
python3 <sebaroDesign>/tools/export_system.py sebaro --target web --out <this directory> --exclude-products <private exclusion list>
python3 <sebaroDesign>/tools/export_system.py --verify <this directory> --exclude-products <private exclusion list>
node <this directory>/checks/verify-export.mjs --strict    # CI without a sebaroDesign checkout
```

`--verify` exits 1 when a file here was edited or deleted, when its source in sebaroDesign changed, when a fresh export would add or drop files, or when a gate of the system fails; it needs a sebaroDesign checkout. `checks/verify-export.mjs` needs only Node and this folder: it catches edits and deletions here, **not** source drift. Re-export to update.

Add `--from-commit <rev>` to both commands for a clean export from a commit rather than from sebaroDesign's working tree, which often holds an unfinished round; the record names the commit and `--verify --from-commit <rev>` compares with it.

### In the product's CI, without the workshop

This folder brings its own checks: no sebaroDesign checkout, no Python, no copy of `export_system.py`.

```sh
node <this folder>/checks/verify-export.mjs --strict    # this folder is unchanged; needs Node 20+
sh <this folder>/checks/lint-web.sh <a CSS file of the product> <the folder of its .html pages>    # the product's sources keep the rules; needs sh, awk, grep, sed, perl
```

`checks/verify-export.mjs` checks this folder (or the export folder given as its argument) against `sebaro-export.json`: every recorded file present and unchanged. One line per finding (`FAIL  missing in target: …`, `FAIL  edited in target: …`, `WARN  not part of the export: …`) and a summary line. Exit 0 no errors, 1 a missing or edited file (with `--strict` also a file the record does not name, without it a warning), 2 usage error or a missing or unreadable `sebaro-export.json`. `--strict` never counts `sebaro-export.json` itself, dotfiles or anything in a dot folder; anything else the product puts into this folder fails it, so keep the product's own files outside (an installed package's `package.json` fails it too: run it there without `--strict`). It does **not** see source drift or the system's gates: that is the workshop's `--verify` above.

`checks/lint-web.sh` is the lint script of the system's spec (rules L1-L8, `spec/03-signature.md`, „### 1.4 Checks“), byte for byte what `tools/lint_rules.py sebaro --print colour` prints for the exported commit. Exit 0 no violation, 1 a violation, with the offending lines printed. It holds the spec's shell rules only: what `lint_rules.py` checks in Python on top of them is not in it and stays a workshop check.
